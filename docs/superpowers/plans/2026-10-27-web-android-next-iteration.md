# 营期日程下一轮迭代计划：网页 + 安卓

日期：2026 年 10 月 27 日  
版本：v0.2，用户已确认范围及首批话术细节  
当前基线：安卓 1.6.2；原有日程网站及其「提交 Issue」入口  
当前阶段：开始本地实施；继续禁止提交、推送和部署

## 1. 这次要解决什么

让日常工作形成一条能查、能整理、能再次使用的路径：

**随手记录 → 提交 Issue → 周三通过 Codex 整理 → 本地 SOP / 必要排期更新 → 手动同步飞书 → 在任务中使用话术。**

日程仍是主功能。记录时不增加分类、关联 SOP、选择优先级等必填步骤；整理工作留给电脑上的 Codex。新增内容放在次级入口和任务详情中。

### 已确定的范围

用户已认可四项迭代：提交记录、多份草稿、补齐周三处理流程、任务内话术卡片，并要求网页和安卓一起做。

网页继续在**原有网站上保留一个小入口**，复用现有 `issue-intake.html`；草稿和记录放在这个入口里面，话术放进现有任务详情。网页主日程不增加新的大型看板或独立工作台。安卓保留「今日、营期、随手记、设置」四项导航。

此前“只保留一份草稿、不做提交记录列表”的首版限制，由本次授权更新为“多份本机草稿 + 轻量提交记录”。其他已有约定继续有效：各人使用自己的私有仓库、无需部署新服务器、飞书手动同步、不提交或推送现有项目代码。

## 2. 已确定的四项功能

### 2.1 提交记录：提交之后找得到

**入口：** App 的随手记右上角增加「记录」；网页现有提交页增加同级入口。主输入页不常驻一长串历史。

**列表展示：** 标题、提交时间、仓库、Issue 编号及可核实的状态。默认按最近提交排序，每次加载 20 条，继续查看时再加载。点记录可打开对应 Issue；不在首版增加远程正文编辑器。

| 情形 | 展示与行为 |
| --- | --- |
| App 已收到 GitHub 创建成功回执 | 显示“已提交”及编号，保存到本机历史；联网时可读取该仓库实际 Issue 列表 |
| App 提交超时，结果未知 | 保留对应草稿，显示“待核对”；沿用草稿唯一标识核对，不能直接重发 |
| 网页刚打开 GitHub 新建页 | 显示“已打开 GitHub，待确认”，保留原草稿；不冒充提交成功 |
| 网页中希望登记成功记录 | 提供可选的“关联已提交 Issue”：粘贴当前仓库的 Issue 链接，记为“本人已关联”，跳官方页核对；不强制每次填写 |
| 要查所有设备的提交 | App 在授权范围内查询 GitHub；网页保留“查看仓库全部记录”，打开该仓库的官方 Issues 页面 |
| 网络或权限不足 | 区分“本机记录”“上次更新”和“无法刷新”；不把缓存说成实时结果 |

**提交状态与处理状态分开。** “已提交”只说明 GitHub 已接收；“待处理 / 待确认 / 已完成”来自电脑看板的业务流程。Issue 的 open / closed 也不能直接换算为 SOP 是否入库。

处理进度首版以 GitHub Projects 看板为准，记录页提供看板入口和 Issue 内的最近处理说明。当前手机授权只有 Issues / Contents，不能假定已能读取 Projects。开发前先做只读能力核验；如缺少权限，页面明确提示“在看板查看”，不擅自扩大授权、不维护另一套会与看板打架的状态。确需在 App 内直接展示实时看板列状态时，另列最小授权方案确认后接入。

### 2.2 多份草稿：一条没提交，也能接着记

**入口：** 随手记保留当前编辑器，增加「草稿」入口与数量提示；“存下这条，再记一条”保存当前内容后打开空白稿。网页同样放在现有提交页中。

**默认规则：**

- 草稿标题仍取首个非空行；列表只展示标题、更新时间及图片数量。
- App 每份草稿保留文字和所选原图，继续遵守每条最多 9 张、单张不超过 10MB 的限制。
- 网页首版草稿保留文字；图片继续在 GitHub 官方提交页添加，避免引入额外上传流程。
- 文字或图片有实际内容才成为草稿；不堆积空白稿。不自动淘汰旧稿，不按天数删除。
- 只有保存成功才切换到另一份或创建新稿。保存失败留在当前稿并提示保留原文。
- 删除单稿需要确认；本机删除不删除已上传的 GitHub 附件。首版不提供“一键清空全部”。
- 每份草稿有独立且稳定的标识。重试、附件路径、结果核对都按该标识处理，不按标题判断是否重复。
- 同时只提交一份；某份失败或待核对时，可以继续编辑其他稿。待核对的那份保留锁定与核对入口。
- 草稿记录目标仓库；切换仓库不自动改投旧稿。多稿功能不引入多账号同时登录，账号切换沿用现有保护规则。

**升级迁移：** 现有单稿及图片完整迁入第一份草稿；原草稿标识、已上传附件标识、待核对状态保持不变。迁移失败保留旧存储，不覆盖成空稿。现有成功回执有就转为一条历史，没有就显示空历史，不生成虚构记录。

草稿仅存当前手机或当前浏览器，不承诺设备之间自动同步。提交到 GitHub 后，记录才可通过同一仓库在其他设备查看。

### 2.3 周三处理流程：补齐已有约定

电脑继续使用 GitHub 自带 Projects 看板。看板负责显示状态，Codex 负责阅读、提出方案和修改文件；不开发新的电脑看板，不在网站或 App 中放“AI 自动入库”按钮。

**三列不变：**

| 看板列 | 含义 | 操作人 |
| --- | --- | --- |
| 待处理 | 尚未整理的新记录及往周遗留 | 新条目加入看板；自动加入不可用时可手动加入 |
| 待确认 | 有冲突 / 缺信息，或本地已入库但待同步飞书 | Codex 按实际处理结果回填具体原因 |
| 已完成 | 本地及必要排期已更新，飞书也已人工同步 | 用户同步后亲自确认、移动卡片 |

**周三执行步骤：**

1. 用户在电脑主动发起本批处理；不设无人确认的定时改写，也不擅自确定周三几点。
2. Codex 读取待处理 Issue、图片、当前 SOP 和排期；先给出逐条入库建议、重复项、冲突和缺失信息。
3. 用户确认本批内容后，再备份和修改本地文件。未确认条目不混入已批准修改。
4. 话术和说明调整只更新 SOP / 对应话术资源；新增任务或更改周次、执行时间，才同步网页与安卓排期。
5. 每条 Issue 回填：本次处理结论、文件与章节、关键改动、涉及的排期、验证结果、待同步飞书内容。
6. 本地已入库的条目进入“待确认”，写明“待同步飞书”；冲突条目写清实际问题。
7. 用户手动同步飞书，核对后亲自移至“已完成”。不自动关闭 Issue，也不使用“关闭 Issue 就完成”的看板规则。

**当前依赖：** 私有仓库已经存在；Projects 看板尚需电脑账号完成官方 `project` 授权及配置。本次只写计划，不执行授权或创建看板。后续配置复用已有脚本，并保留已有项目和卡片。

### 2.4 任务内话术卡片：需要时才展开

**入口：** 网页现有任务详情、App 原有任务详情中增加「相关话术」区域；任务列表不塞话术全文，没有关联话术时不显示空卡片。

**卡片内容：** 适用对象 / 场景、可复制正文、必要的内部备注、SOP 来源及版本。给学员、给讲师、给 AI 的文字明确区分；“复制话术”只复制对外正文，不夹带内部备注或来源说明。

一项任务可关联多条话术，先展示标题，点击展开。复制成功给轻量反馈。首版不加入编辑、富文本排版或自动发送到飞书群等操作。

**内容来源与更新：**

- 由 Codex 从已确认的本地 SOP 中提取，经用户确认后进入可分发话术资源。完整 SOP、未确认内容和学生个人资料不直接打入网站或 APK。
- 一份结构化话术资源供网页和 Android 导出使用；保留话术标识、版本、来源文档 / 章节及适用范围。
- 使用稳定任务标识关联，不靠任务标题相似度自动匹配。开发时先核验现有任务键，再确定映射；不改变已完成任务的键。
- 用户下次修改 SOP 后，由 Codex检查关联话术是否需要同步更新，生成差异并验证；App 不假装能直接读取电脑上的最新 SOP。
- 网页加载自己发布版本的资源，App 使用安装包内资源；界面可查看内容版本。没有新的发布或覆盖安装，就不宣称两端已自动更新。
- 含本期链接、讲师姓名等未确定变量时，保留原文并清楚提示需补充，不自动编造替换值。

**建议先选 3～5 个高频场景试用：** 老带新、课程发布提醒、作业 / 督学提醒等。必须先核对新版 SOP；未整理好的课程提醒不凭推测补写。

已确认时间继续遵守：第 3、11 周老带新在周三、无固定时刻；第 12 周仍是周日结营直播之后。本功能不顺带调整这些提醒。

## 3. 我补充的建议

以下属于新增建议，并非已批准开发的功能。推荐先讨论前两项，避免一次扩成复杂工作系统。

| 建议 | 具体作用 | 建议阶段 |
| --- | --- | --- |
| 从任务详情“记一条” | 打开现有随手记并带上可见、可删除的任务名称 / 日期 / 周次来源，便于以后判断适用场景；不新增必填字段、不自动带入学员个人信息 | 四项核心功能完成后，优先考虑 |
| 本批待同步飞书清单 | Codex 整理后给一份按文档 / 章节汇总的变更清单，包含原文、建议替换内容和来源 Issue，减少手动同步遗漏；仍由用户确认完成 | 可随周三流程补充，优先考虑 |
| 话术关键词搜索 | 话术量增加后，在现有入口内搜索关键词；先不增加独立底部导航或复杂知识库首页 | 观察第一批话术使用后再决定 |
| 草稿导出备份 | 网页导出文字稿，App 可导出文字与图片包；不包含 GitHub 授权信息。用于换设备或浏览器清理前备份 | 后续可选，不冒充云同步 |

自动替换营期变量、收藏话术、周三提醒等先留在后续讨论，不作为本轮默认范围。先确认真实使用频率，再增加按钮和配置。

## 4. 网页与 App 怎么一起做

| 位置 / 功能 | 原有网页 | 安卓 App |
| --- | --- | --- |
| 日程主界面 | 保留现有小入口与主布局 | 保留现有四项导航 |
| 草稿 | 现有提交页内的本浏览器多稿 | 随手记内的本机多稿，含图片 |
| 提交 | 延续 GitHub 官方页确认与添加图片 | 延续应用内授权、上传与提交 |
| 最近记录 | 本浏览器跳转 / 关联记录，提供仓库全部记录入口 | 本机回执及授权仓库的实际记录 |
| 处理进度 | 从现有小入口打开 GitHub 看板 / Issue 处理说明 | 提供同样入口；内嵌实时列状态以只读权限核验为前置条件 |
| 任务话术 | 放进现有任务详情 | 放进现有任务详情 |
| 周三入库与飞书同步 | 电脑 Codex + GitHub 看板 + 人工同步 | 用于记录和查阅，不接管入库 |

网页沿用现有免部署方案。**小入口只决定功能放在哪里，不会自动改变 GitHub 登录和授权能力。** 本计划不在原网页中增加密钥输入框、不搭新的登录中转服务器。若之后希望网页也直接读取私有仓库并在页面内提交，另行给出完整授权方案，不能把它当成一个按钮就能完成的小改动。

## 5. 分批实施与交付

| 批次 | 工作 | 可验收结果 |
| --- | --- | --- |
| 准备 | 备份当前本地修改；核验旧稿迁移、稳定任务键、网页能力和 Projects 只读权限；确认样例话术 | 功能边界与数据迁移规则明确，无外部写入 |
| 第一批 | 网页 + App 多份草稿、提交记录和旧数据迁移 | 两端都能连续记多条；失败不丢稿；已打开与已提交分得清 |
| 第二批 | 完成电脑看板配置、周三 Codex 处理模板与逐条回填规范 | 用用户选定的一条真实 Issue 走完整理和人工确认流程；不替用户同步飞书 |
| 第三批 | 选定话术、统一资源及任务关联；网页 + App 详情卡片 | 同一任务两端展示相同版本话术，复制内容正确，主列表保持简洁 |
| 后续可选 | 从任务记一条、待同步清单、搜索或备份 | 按用户确认的建议单独增量交付 |

每批均交付本地可检查版本、改动说明和验证记录；App 使用原签名生成可覆盖安装 APK。网页提供本地预览。正式网站更新、Git 提交 / 推送不包含在当前授权内；不因计划完成就自动上线。

版本号、具体工期在范围确认并完成准备核验后确定，不把尚未验证的能力算入已完成。

## 6. 实现位置与验收重点

本节供后续开发定位，当前不改这些业务文件。

| 模块 | 预计涉及位置 | 核心验收 |
| --- | --- | --- |
| 网页入口及多稿 / 记录 | `index.html`、`issue-intake.html`、`issue-intake.js`、`issue-intake.css`；需要时拆出单独的存储模块 | 主界面改动小；刷新读回；多标签编辑冲突不静默覆盖；存储失败不切走当前稿；跳转不记成成功 |
| 安卓多稿 / 记录 | `IssueStore.kt`、`IssueCaptureViewModel.kt`、`IssueCaptureScreen.kt`、`GitHubIssueClient.kt`；草稿列表 / 历史按职责拆屏 | 旧稿及图片迁移完整；账号 / 仓库隔离；强退恢复；结果未知先核对；不重复创建 Issue；历史排除 PR |
| 周三流程 | `scripts/setup-issue-project.ps1`、`docs/github-issue-setup.md`、本地 SOP 维护规范 | 保留既有卡片；三列含义统一；冲突与待同步可区分；飞书同步前不标完成 |
| 话术资源 | 拟新增独立话术资源与校验 / 导出脚本，复用现有 Android 资源导出链路 | 原文、对象、适用周次、来源完整；任务关联稳定；缺失变量不编造；禁止误将内部备注当群发话术 |
| 两端任务详情 | 网站现有任务详情渲染、Android `TaskDetail.kt` | 一键复制只含正文；窄屏 / 大字体 / 键盘下按钮可达；不改变任务完成状态、日期或提醒 |

**升级与失败场景必须验证：** 单稿升级、多稿切换途中保存失败、草稿带原图、断网与授权失效、提交超时后重新核对、仓库切换、历史分页失败、浏览器多标签、缺失话术映射，以及旧版排期和完成记录保持有效。

使用隔离的临时数据、测试仓库或用户指定条目验证写入；不往真实 SOP 写测试夹具。网页测试按模块增加用例，Android 增加迁移 / 状态测试，最后对网页与模拟器做实际交互检查。参考命令沿用 `npm test` 及 Android `testDebugUnitTest lintDebug assembleRelease`，具体回归步骤在各批开发计划中展开。

## 7. 开发前需要拍板的细节

以下有推荐默认值，便于一起确认，不代表已经实施：

1. **入口名称：** 网站主入口暂保留“提交 Issue”，进入后展示草稿 / 记录；App 继续叫“随手记”。不为了统一名字重做主导航。
2. **网页历史：** 接受“本浏览器记录 + GitHub 官方全部记录”的轻量方案；网页不默认新增直接读私有仓库的授权链路。
3. **处理状态：** Projects 为唯一进度依据；先提供看板入口，内嵌读取权限先核验。是否值得增加只读授权，再决定。
4. **首批话术：** 推荐先选 3～5 个高频场景，逐条确认新版原文。后续按使用反馈扩充，不整份 SOP 一次性塞进客户端。
5. **附加建议：** 优先考虑“从任务记一条”和“本批待同步飞书清单”，搜索与备份后置。

用户已确认计划与默认方案。首批话术确定为老带新、课程发布提醒、作业 / 督学提醒、直播答疑提醒；缺失或矛盾原文逐条列出，不自行补写。存在【课程链接】【讲师姓名】等待填内容时，允许复制，并在复制前后明显提示需要补充。未确定的自动变量替换不纳入首版。

实施从多稿和记录开始，随后补齐可在本地完成的周三流程与话术卡片。Projects 的真实外部授权、飞书人工同步及正式发布仍按原边界处理。

- GitHub REST 支持浏览器跨域调用，但获取私有资源所需的用户授权是另一环；不能把 REST 的 CORS 支持当成网页已经登录。见 [REST 跨域说明](https://docs.github.com/en/rest/using-the-rest-api/using-cors-and-jsonp-to-make-cross-origin-requests) 与 [GitHub App 用户授权](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app)。网页继续沿用当前流程属于本项目的范围选择。
- Projects 通过 GraphQL 读取 / 更新，另有授权要求。见 [Projects API 与授权](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-api-to-manage-projects)。本计划不假定现有手机仓库权限已经覆盖看板。
