## 1. 要做成什么

手机负责记录，GitHub 负责收集和展示，Codex 负责整理。原有日程提醒继续使用；手机新增入口是一页简单的提交表单。

| 环节 | 已确认的行为 |
| --- | --- |
| 手机入口 | 原安卓 App 底部新增随手记，顺序为今日、营期、随手记、设置 |
| 文字 | 用户手动粘贴 ChatGPT 整理后的内容；标题自动取第一行 |
| 填写负担 | 不填分类、关联 SOP、营期等结构化字段，由 Codex 后续整理 |
| 图片 | 添加图片、相册多选、缩略图预览及移除；每条最多 9 张、单张不超过 10MB、保留原图 |
| 草稿 | 自动保存最后一份文字及图片；不做草稿列表或提交记录页 |
| 提交 | 全部图片上传完成后创建 issue；成功清空表单并显示编号，失败保留草稿 |
| 结果不明 | 网络中断后先核对 GitHub，再决定是否重试，防止重复 |
| 存储 | 每个人提交到自己的仓库，图片与 issue 位于该仓库；owner/sop-inbox 仅为原用户的个人实例 |
| 手机授权 | 已确认 GitHub App 设备授权：App 显示短码，用户在 GitHub 官方网页确认，返回 App 选仓库；手机直连 GitHub，无自建授权服务器 |
| 电脑 | GitHub Projects 看板，浏览器打开，不另做软件 |
| 看板三列 | 待处理、待确认、已完成 |
| 入库 | 周三由用户主动发起；Codex 先提方案与冲突，确认后修改本地 SOP 和必要排期 |
| 飞书 | 用户手动同步；同步完成后由用户拖到已完成 |
| 项目发布 | 网站/App 项目不提交、不推送、不部署，交付本地 APK |

## 2. 手机页面和交互

页面上方显示“随手记”，正文区用于粘贴多行文字。下方是“添加图片”及已选图片缩略图，再下方是提交按钮。授权配置放在设置入口，不作为每次提交的字段。

文字按原样保留 Markdown 和链接。点击提交后显示当前上传/提交进度，并阻止重复点击；网络工作在后台执行，表单保留可见。一次只处理当前一份草稿，不引入自动提交队列。

选择图片后复制原始文件到 App 私有草稿目录，确保关闭 App、重启后仍能恢复，不仅保存可能失效的相册临时引用。只读取用户主动选中的文件。超出数量或大小时立即说明原因，已有合法内容保留。

首次点击“连接 GitHub”后，App 显示短授权码并提供复制和打开 GitHub 官方设备授权页的入口。用户在 GitHub 输入/粘贴短码并确认，返回 App 后核对账号、选择目标仓库，不要求复制 Token。采用 GitHub App 的细粒度仓库授权，所需权限仍为 Issues 与 Contents 读写，限定用户选择的仓库。App 使用 Android Keystore 保存本机授权，不打包任何用户凭据；连接检查只读取信息，不创建测试 issue。授权失效时保留草稿并引导重新连接，提供退出/移除本机授权入口。原 v0.2 手动填写 fine-grained token 的方案由网页授权替代，不额外保留第二套手动配置模式。

初版不扩展系统分享接收、自动导入 ChatGPT、草稿列表、提交历史、语音上传和手机端 AI 调用。

## 3. 图片上传与可靠提交

采用 GitHub 仓库文件 API，将原图放在 `attachments/<草稿唯一标识>/` 下；文件名带序号及内容标识。issue 正文引用该仓库的相对图片路径，不使用临时下载 URL。GitHub 官方支持在 issue 中引用仓库图片，见 [图片引用规则](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#images)；文件写入所需权限见 [Contents API](https://docs.github.com/en/rest/repos/contents#create-or-update-file-contents)。

每份草稿有持久化唯一标识，文字提交时将标识写入不可见注释。流程为：

1. 检查文字、图片、授权与当前草稿是否存在未确认的提交。
2. 按顺序上传图片，记录已成功的文件及内容标识。
3. 全部图片成功后，创建含正文及图片引用的 issue。
4. 收到 GitHub 确认的编号和链接后，清空该草稿并显示成功回执。
5. 图片失败时不创建 issue，保留整份草稿；重试复用已经上传且内容一致的图片。
6. 创建请求中断时，保留“结果未确认”状态，先分页核对同一草稿标识；找到则按已成功处理，完整核对未找到才允许重试。核对本身失败时保持草稿，不自动再次创建。

上传中退出 App 时也不得丢失草稿标识和上传记录。不会自动删除远端图片，避免误删已被 issue 引用的附件。未提交或废弃草稿遗留的已上传附件记录在本地，后续可由用户指定清理，不另做首版清理管理界面。

## 4. 电脑看板

为原用户创建个人私有 GitHub Project，关联 owner/sop-inbox，设为 Board 视图；Status 只有待处理、待确认、已完成。

| 状态 | 含义 | 谁改变状态 |
| --- | --- | --- |
| 待处理 | 新提交、尚未入库 | 新记录自动加入 |
| 待确认 | 存在冲突/缺信息，或本地已入库但待同步飞书 | Codex 根据实际结果回填并移动 |
| 已完成 | 本地与必要排期已更新，飞书也已由用户同步 | 用户同步飞书后亲自拖动 |

待确认中的卡片应有明确说明，例如“问题待确认：作业截止时间”或“本地已入库，待同步飞书”。不增加第四列。

使用 Projects 的内置工作流自动加入该仓库的新 issue，并在加入时设为待处理；手机无需 Projects 写权限。已有 issue 若未自动加入，配置时单独补入。自动加入不是实时成功回执，手机成功以 issue 创建成功为准。官方行为见 [自动加入项目](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/adding-items-automatically)。

Projects 设置与 Codex 修改列状态需要电脑账号的 project 权限。当前 CLI 授权未包含此权限；正式实施时向用户说明并通过 GitHub 官方授权流程追加。手机仍只持有单仓库令牌。权限依据见 [Projects API 授权](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-api-to-manage-projects)。

看板不开发自定义 AI 或入库按钮，使用 GitHub 自带查看、搜索、筛选、详情和拖动能力。issue 的编辑/删除保留为 GitHub 原生操作，不额外做手机或桌面管理功能。

## 5. 周三由 Codex 整理

用户主动在电脑 Codex 发起，例如：“按项目 SOP 入库规则，处理本次待处理的 issue。”不建立无人确认的定时执行，也不需要固定周三几点。

Codex 先读取看板待处理卡片、正文和图片、本地维护规范、对应 SOP 及必要排期配置，列出：来源编号、拟入库文件与章节、建议修改、冲突或缺失信息、是否涉及排期。此时不改正式 SOP。

用户确认本批方案后：

1. 备份本地原文及相关配置，有针对性地修改，保留未改段落、附件相对路径。
2. 按内容分类和关联 SOP，不要求用户回手机补填字段。
3. 话术、说明文字仅修改 SOP；执行事项、时间、教学周次变化才修改共享排期。
4. 排期变动时同步网站 data.js 与 Android 导出资源，保持已有任务完成标识；运行对应检查，静态资源变化需重新构建 APK。
5. 未确认的时刻、周次或适用范围留待确认，不自行补齐。批准处理的其他条目可独立推进。
6. 每条 issue 回填处理记录，并移至待确认，注明待同步飞书。
7. 用户手动更新飞书，核对完成后亲自将卡片拖到已完成。

处理记录至少包含：

- 来源 issue 编号、处理日期。
- 本地 SOP 文件、章节和实际改动。
- 排期是否涉及；涉及时记录变化、验证结果和新 APK 的位置。
- 需要用户同步到飞书的文档、章节及文字/图片内容。
- 未解决的问题，以及当前是待确认口径还是仅待同步飞书。

## 6. v0.2 已获认可的补充默认项

以下已随 v0.2 整体审阅获用户认可；新增多人使用不改变这些原则，涉及账号或仓库切换的适用方式需补充确认：

1. 正文至少有一行非空文字；只有图片时提示补一句说明。标题取第一条非空行，过长只截短标题，正文不删减。图片支持 JPG、PNG、WebP、GIF，其他格式提示换图，不自动转码；10MB 按 10,000,000 字节判断。
2. 默认整理所有仍在待处理列的 issue，包括往周遗留；用户指定编号或日期时遵从当次指令，不重复处理待确认或已完成卡片。
3. Projects Status 是进度依据，首版不把拖到已完成自动映射为关闭 issue，并禁用会因 issue 关闭就自动标为完成的工作流，避免跳过飞书同步确认。
4. 手机沿用现有 MiSans、配色及原生组件；电脑采用 GitHub 自带界面，不重做 UI。
5. 用隔离夹具完成主要测试，最后由用户提交一条明确标记的测试记录做手机—GitHub—看板验收。测试条目是否保留或删除由用户决定。

## 8. 验收标准

- 原安卓 App 底部新增随手记，现有日程、营期、完成状态与通知功能正常。
- 复制粘贴文字、标题生成、图片多选/移除/超限提示正常。
- 关闭重开后文字与原图草稿可恢复；成功后只清除已成功的草稿。
- 授权缺失、失效、上传失败、断网均保留文字及图片。
- 图片部分上传后重试不重复上传相同内容；issue 创建中断后先核对，不盲目重发。
- 私有仓库 issue 与看板中能看到图片，Codex 可通过授权读取原图。
- 新 issue 进入待处理；本地入库后为待确认；只有用户同步飞书并拖动后才为已完成。
- Codex 先提方案，确认后改本地 SOP；必要排期同时更新网站和 Android，保留已有任务标识。
- 网站测试、Android 单元测试、lint、release 构建与签名检查通过；不以模拟检查冒充手机真实验收。
- 交付本地 APK、看板地址、手机授权步骤及 Codex 使用说明；没有提交或推送现有项目代码。

## 10. 新增：同事也能配置自己的 GitHub（待讨论）

### 已明确的新增需求

App 后续可能分享给同事使用，手机端必须方便配置各自的 GitHub。不能在 APK 内固定原用户身份、令牌和 owner/sop-inbox 作为所有人的提交目的地。每位使用者的授权在自己的设备保存。仅增加 GitHub 配置能力，不据此扩展原有日程的账号、团队或数据权限。

### 配置页面及衔接细节

计划在“设置 → GitHub 配置”连接账号，显示用户名及当前提交仓库，可更换仓库、检查连接、退出或更换账号。设备授权、仓库选择/跳转新建和切换前先提交/清空草稿均已确认。首次进入随手记、尚未配置时给出配置入口。每次提交前清楚显示目的仓库。先支持一台设备当前使用一个账号、一个提交仓库，不做多账号并行管理。

### 需一起确认

1. **已确认：每个人提交到自己的仓库，各自管理资料与看板，不采用共享团队仓库。** owner/sop-inbox 不作为同事默认目的地；不创建账号之间的内容共享或自动合并。
2. **已确认：采用 GitHub App Device Flow（设备授权），无需部署服务器，不手动填写 Token。** 用户在 GitHub 官方网页确认 App 提供的短码。管理员一次性注册一个可供同事安装的 GitHub App，并开启 Device Flow；普通使用者授权自己的仓库，不必各自注册应用。权限仅为所选仓库 Issues/Contents 读写，App 显示实际身份与目标仓库；用户授权与仓库安装授权均需完整处理。
3. **已确认：已有仓库时在 App 中选择；没有仓库时点“新建仓库”，跳到 GitHub 创建私有仓库，回来刷新选择。** 不在 App 中自动建仓库，不申请仓库创建管理权限。新仓库若尚未加入 GitHub App 授权范围，应引导用户在 GitHub 授权后再刷新，不能只凭已登录就认为可访问。
4. **已确认：有未提交草稿时，先提示提交或主动清空，再允许更换账号/仓库。** 不把旧账号/仓库的文字和图片默默转到新目的地。结果未确认的提交必须先按原账号、原仓库核对；同一账号重新授权不视为换号，不丢弃草稿。已上传附件仍属于原仓库，不自动删除。
5. 各人沿用独立 Projects 看板的使用模式；首次是提供配置指引还是由软件自动创建，仍待确认。未授权前不操作同事的仓库或项目。

目前只更新计划。未注册新的 GitHub 登录应用，未创建同事仓库、修改授权或编写配置界面。

### 已确认：手机直连 GitHub 的免部署设备授权

1. 管理员先在 GitHub 注册一个供同事安装的 GitHub App，开启 Device Flow。只将公开 client ID 配置到 APK，不生成或嵌入运行所需的应用密钥/私钥，不运营登录中转服务。
2. App 直接向 GitHub 请求设备码，展示短授权码及官方验证网址。
3. 用户在 GitHub 官方网页输入短码并确认，App 按返回的 interval 等待并轮询；用户返回 App 后恢复核对，支持取消、拒绝和过期重试。
4. 成功后读取实际 GitHub 身份及已安装授权的个人仓库，选择后保存本机配置。没有仓库时按已确认流程跳 GitHub 新建，并按需给新仓库授权后刷新。
5. 令牌与刷新令牌使用 Android Keystore 保存；设备授权取得的刷新令牌可由手机直连 GitHub 续期，不需要 client secret。刷新轮换时持久化新凭据，旧凭据失效或授权被撤销时引导重新连接并保留草稿。
6. 用户拒绝、设备码到期或取消时停止轮询；slow_down 时按 GitHub 返回的规则延长间隔。一次只进行一个授权/续期流程，避免同时轮换凭据。
7. 不部署自建服务器，不使用 Netlify、不购买域名、不新增数据库。GitHub App 注册与仓库/看板配置是 GitHub 账号设置，不是服务部署。
